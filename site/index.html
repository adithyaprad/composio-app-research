How the agent works

A pipeline of loops, not a single run. The agent fills every row; a rule checker and a browser pass re-check it; people write the answer keys and look at what the agent flags.

Run it with one command

python -m agent all --input apps.csv --run-id my-run

Runs research → rule check → browser check into data/runs/my-run/pass1..3, then writes rows.jsonl, final.json, final.csv, needs_human.jsonl, needs_human.json, summary.json. --dry-run runs offline with fakes.

What each stage does

Pass 1 · Research agent
Searches official docs, fills one schema row per app from fetched text only, and quotes the sentence behind each claim. Evidence URLs must be pages it actually fetched; quotes must appear in the page text; consistency validators catch contradictions. Model: global.anthropic.claude-sonnet-5-5.
Pass 2 · Rule checker
Re-checks every row against general rules (no app names). Code fires a rule only when notes or a vendor quote show the pattern; one LLM reviewer call per row can name more. Only the fields behind a fired rule are re-researched.
Selector
Code picks rows that still look shaky. Reasons:
  • 33 confidence is medium or low
  • 15 notes mention a demo/sales gate, a coming-soon or beta MCP/API, or an unreadable page
  • 8 pass 2 logged unsupported evidence or validation errors
  • 6 a page cited for a deciding claim came back thin, blocked or failed
Pass 3 · Browser Use
Renders each flagged row's pricing, signup, auth and MCP pages in a real browser and saves a screenshot. Only a blocked, captcha or empty page is retried on a cloud browser (17 cloud sessions). The same LLM reads the rendered text and may confirm or fix only the flagged fields, with quotes found on the page. It reads pages; it does not click or navigate.
Scoring
scripts/score_gold.py compares each pass to locked hand labels. A row counts only if every critical field is right and evidence is present.
Patterns + this page
scripts/patterns.py clusters the final rows; scripts/build_site.py renders this page and scripts/check_site.py re-checks every number.

How the answer keys were built
  • Gold (20 apps, 2 per category). Labelled by hand from official docs without looking at the agent's rows, then audited field by field against current vendor docs. The audit corrected 3 apps' scored labels and clarified the rubric (schema/GOLD_AUDIT.md).
  • Sealed holdout (10 apps). A seeded random draw, one per category, excluding gold and pilot apps. Labelled and locked before the pass-2 rules were written, scored once per frozen pass, and never used to write a rule.
  • Gated counts as correct. Where an app is behind a sales or partner gate, saying so with the vendor page as evidence is the right answer and is scored that way.
  • Strict row score. A row is right only if auth, access, API, MCP, verdict and blocker all match and every claim has evidence.

Limits

  • Pass 3 only reads pages: it does not click, navigate, follow links, open tabs or expand sections, so a fact one click away is missed.
  • Auth is the weakest critical field on the holdout (60%); which method is primary is a judgement call the rules do not settle.
  • Needs-customer-admin scored 70% on gold and 10% on holdout; API breadth 65% on gold. Treat both as rough.
  • The answer keys are small: 20 gold and 10 holdout apps.
  • Gold informed some checker rules; the holdout is the cleaner test and stayed at 3 of 10 whole rows.
  • Evidence scoring checks that each claim has a URL; whether the page truly supports the claim was checked by people on samples only.
  • Composio Instant tool execution was never connected for this project, so it did no research work.
  • A snapshot: vendor docs change, and this data is as of 2026-11-23.
